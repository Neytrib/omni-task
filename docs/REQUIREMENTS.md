# Requirements and verification map

This map separates the assessment baseline from the product choices added by the user. The confidential assessment is summarized in [SPEC.md](../SPEC.md); its PDF and extracts are deliberately absent from this project. Public hosting, a particular authentication scheme, drag-and-drop, and themes are not assessment mandates.

The full suite was rerun during **S9 on 2026-09-30**: **382 backend tests passed**, **125 frontend tests passed across nine files**, and TypeScript checking, the production frontend build, and Ruff checks passed. Clean-source startup, private HTTPS/WebSockets, and actual backup/restore rehearsals also passed. [TASKS.md](../TASKS.md#s9---submission-and-vps-deployment-preparation) records commands, results, warning details, and limitations. Test names below identify executable checks; they are not substitutes for the remaining manual checks. Arc observations cited from S7/S8 remain historical.

## Reproducing the automated checks

After following [README setup](../README.md), run from the project root:

```sh
python3 scripts/test_backend.py -q
npm --prefix frontend test -- --reporter=dot
npm --prefix frontend run typecheck
npm --prefix frontend run build
.venv/bin/ruff check omni_logging.py backend bot scripts tests deploy
.venv/bin/ruff format --check omni_logging.py backend bot scripts tests deploy
```

The backend runner uses a disposable PostgreSQL database and isolated Redis namespaces/channels; integration tests start separate workers/API processes. It does not use SQLite as evidence for PostgreSQL behavior. External Telegram and transcription transports are fake, so this suite does not incur paid transcription. Frontend tests use a DOM environment, not a browser. Record the output of a future run rather than treating the counts above as a new result.

## Evidence limits and remaining manual checks

- S8 Arc desktop inspection covered creation, safe multiline/literal-HTML display, complete details, keyboard status change, delete Cancel/Confirm, focus restoration, timed notice dismissal, and recovery to Live after API restart. S7's separate two-tab/offline/logout observations remain historical evidence.
- Phone layouts/physical-phone use, actual light-theme rendering, 200% zoom, and whole-card pointer dragging still require manual Arc checks. Component tests and a successful production build do not establish those visual results. Native Arc controls intermittently timed out; no substitute browser was used.
- S8 did not repeat the complete real Telegram/OpenAI voice journey or test a second actual Telegram account in Arc. Automated two-user isolation and fake voice-worker coverage passed. The [demo script](DEMO.md) is a future walkthrough, not execution evidence.
- Durable source uniqueness means repeated deliveries create at most one task per source. External provider requests and Telegram sends cannot share a PostgreSQL transaction: ambiguous success before a checkpoint can repeat a provider call or fallback notification. Exactly-once billing or external delivery is not claimed.
- Container-recreation/restart tests do not prove recovery from disk loss, corrupted backups, power loss, or a production outage. S9 preparation does not by itself mean a VPS was purchased or the application publicly deployed.
